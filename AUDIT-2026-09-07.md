# 1. Shield ZK circuit soundness

# ZCrypt v2 shield circuit audit (read-only)

Scope read in full: `/Users/chris/Desktop/Development/zcrypt-v2/impl/shield/src/{lib.rs,tall.rs,tree.rs,zvm.rs}`, `/Users/chris/Desktop/Development/zcrypt-v2/impl/core/src/shield_tx.rs`, the SHIELD apply/check paths in `/Users/chris/Desktop/Development/zcrypt-v2/impl/core/src/node.rs`, plus the vendored `p3-uni-stark 0.6.1` verifier, `p3-fri` hiding PCS, `p3-monty-31` integer conversion, and the ABCI REGISTER/mint handlers needed to confirm one finding. Production path is `tall.rs` (`lib.rs:1039-1063` routes `prove`/`verify` there); nothing in core/abci/bridge/wallet calls `verify_wide`. Note: the brief said DEPTH=20; the code is DEPTH=32 (`tree.rs:13`, `tall.rs:49` HEIGHT=128).

## Verified sound

- **Conservation is an integer identity, not just a field one.** Each of the 4 coins has lo and hi limbs range-checked to 26 bits (`tall.rs:191-194`, wide `lib.rs:478-481`), fee to 26 bits (`tall.rs:240-241`, `lib.rs:578-579`), carry E+8 to 4 bits (`tall.rs:260-261`). With p = 2^30.9: d ∈ (−3·2^26, 2^27), 2^26·E ∈ [−2^29, 7·2^26], so d − 2^26·E ∈ (−p, p) and `tall.rs:262` / `lib.rs:606` forces Σin = Σout + fee over Z. No wraparound path exists.
- **Dummy input cannot inflate.** act boolean (`tall.rs:200`); (1−act)·lo = (1−act)·hi = 0 (`tall.rs:202-203`). Contrapositive: any nonzero value forces act=1, which forces root binding.
- **All 16 lanes of every core Poseidon2 block are bound.** Commit block: [0][1] bits, [6..14] = pk block output (`tall.rs:210-212`), [14] shared asset (`tall.rs:185-187`), [15]=0 (`tall.rs:208`, outputs `tall.rs:232`). Pk block: [8..16]=0 (`tall.rs:213-215`). Nullifier block: [0..8] = pk block's spend secret (`tall.rs:217-219`), [8][9] = value limbs, [10..14] = blind, [14] = asset, [15]=0 (`tall.rs:220-226`). So nullifier is canonical per (coin, secret) and computed from the same secret whose pk is in the commitment.
- **Nullifiers and output commitments bound to public inputs on row 0** (`tall.rs:228-230`, `233-235`; wide `lib.rs:567`, `573`).
- **Merkle membership (tall chain).** Selectors are AIR-defined and committed by the verifier itself (`tall.rs:92-116`, `561-564`); uni-stark uses the vk's commitment, not the proof's, checks `vk.degree_bits == proof.degree_bits`, and observes it in the transcript (`p3-uni-stark/src/verifier.rs:262, 315-324, 409-411`). `commit_preprocessing` is zero-padded (`p3-fri/src/hiding_pcs.rs:133-152`) and the salts come from the fixed seed-0 RNG, so prover and verifier derive identical keys. Chain: row0→row1 leaf feed (`tall.rs:303-309`), input 1 leaf via carried CLEAF (`tall.rs:264-268`, `313-318`), per-row link (`tall.rs:321-327`), dir booleanity on path rows (`tall.rs:290`), root binding gated by carried CACT (`tall.rs:329-337`), carries constant via `when_transition` (`tall.rs:163-171`). P_CHAIN correctly excludes each input's last row so input 0's root never leaks into input 1's leaf. Direction semantics match `tree.rs:121-133` / `root_from_path` (`tree.rs:138-148`). The unused R_PSIB column (`tall.rs:291-298`) is harmless.
- **Node-side anchor and double-spend gates.** Root must be in the 256-entry window before verification (`node.rs:1526-1531`), nullifiers checked against the SMT then inserted (`node.rs:1539-1546`), in-tx duplicate rejected (`shield_tx.rs:249-252`), NULL_NF rejected (`shield_tx.rs:246-248`), canonical limbs enforced on the wire (`shield_tx.rs:340-348`) and again in `verify_tall` (`tall.rs:553-560`), and the registry key reduces mod p (`shield_tx.rs:62-72`).
- **Public-input binding.** Verifier requires exactly `num_public_values` (`verifier.rs:366-374`) and observes all of them before sampling alpha (`verifier.rs:412-418`); chain_domain and aux digest are therefore Fiat-Shamir bound (tests at `tall.rs:690-706` confirm). Aux digest limbs are 28-bit (`shield_tx.rs:131`), canonical.
- **FRI/config.** 112 queries, log_blowup 2, 20+20 PoW bits, degree-5 extension (`lib.rs:96-99`, `115-125`); floor asserted in release (`lib.rs:180-184`); no cfg(test)/feature-gated weaker path exists. `HidingFriPcs` with `ZK = true` (`hiding_pcs.rs:93`) and 4 random codewords; three independent OS-seeded ChaCha20 RNGs per proof (`lib.rs:196-198`). Wide/tall cross-acceptance impossible (preprocessed width/vk mismatch → `PreprocessedVerifierKeyInconsistency`). Workspace uses default `panic = unwind` (no `panic = "abort"` in `impl/Cargo.toml`), so `catch_unwind` in `verify_tall` actually contains verifier panics.
- **VM ≡ circuit.** Every rule in `zvm.rs:89-167` (range, membership/shared root, single asset, conservation, nullifiers with the same `dummy_witness`, outputs) has an enforcing constraint above and vice versa; `shape_ok` (`lib.rs:778-799`) mirrors it. No rule exists on only one side. (The VM never runs on the node, so this is a prover-side spec check, not a consensus gate.)

## Findings

### 1. CRITICAL: asset-id namespace collapses from 64 bits to 31 bits inside the circuit; permissionless registration lets anyone mint counterfeit zBTC or native ZCRYPT
**Location:** `lib.rs:617` (`s[14] = BabyBear::from_u64(asset_id)`), `lib.rs:634` (same in `nf_input`); `p3-monty-31/src/monty_31.rs:532-534` (`from_int(u64)` → `to_monty_64`, reduces mod p); `asset_registry.rs:44-51` (`asset_id_for` returns a raw 64-bit hash), `asset_registry.rs:135-138` (uniqueness on the exact u64 only); `abci-node/src/main.rs:1125-1140`, `1548-1552` (REGISTER has no authorization; registrant supplies `authority` and `max_supply`); `node.rs:418-461` (`htlc_open` mints against the registrant's own keyset); `node.rs:720-721`, `keys.rs:570` (burn and claim coins built from the u64 id).
**What:** The asset lane in every commitment and nullifier is `asset_id mod 2013265921`. Two registry ids that are congruent mod p produce bit-identical coins. Nothing anywhere canonicalizes asset ids below the field order (grep confirmed), and the registry only rejects exact-u64 duplicates. The `id == NATIVE_ASSET` guard checks `id == 0`, not `id ≡ 0 (mod p)`.
**Exploit:** Grind a ticker T (2..10 alphanumerics, ~2^31 hash trials, minutes on a laptop) with `asset_id_for(T) ≡ asset_id_for("zBTC") (mod p)`, or `≡ 0 (mod p)` to alias native ZCRYPT. Send REGISTER T with `authority = commit(own ML-DSA keyset)`, arbitrary `max_supply`. `htlc_open` + `htlc_claim` mints T coins (`commit_asset(v, blind, pk, id_T)`), which are indistinguishable in-circuit from zBTC (or ZCRYPT) coins. Spend them as zBTC: the single-asset constraint holds (same lane), `htlc_burn_lock` recomputes `expected` with zBTC's u64 id and matches (`node.rs:720-724`), `record_burn` is saturating (`asset_registry.rs:232-236`), and the bridge watcher pays reserve BTC. Or pay victims counterfeit zBTC/ZCRYPT; their wallets recompute the same commitment from the note's u64 id. Unlimited inflation of any asset including the native token.
**Fix:** Make `asset_id_for` return `field_limb(hash)` (or reject/retry when `hash mod p` is 0 or collides), key registry uniqueness on the reduced id, and reject any tx-supplied `asset_id >= FIELD_ORDER` at the wire/registry boundary (`shield_tx`, REGISTER, HTLC, burn, bond). Add `debug_assert!(asset_id < FIELD_ORDER)` in `coin_input`/`nf_input`. Existing registered ids on live chains need a migration check for mod-p collisions (probability negligible for honest ids, but verify).

### 2. MEDIUM: anchor window is 256 *appends*, not blocks; cheap mempool-wide eviction and liveness failure under load
**Location:** `node.rs:137` (`ROOT_WINDOW = 256`), `node.rs:253-262` (one root pushed per appended coin).
**What:** Every transfer appends 4 leaves (main 2 + gas 2), so 64 transfers roll the window entirely. At 1s blocks a proof that took a few seconds to build can already be "unknown/expired" (`node.rs:1529-1531`, `1648-1653`); CheckTx accepts it, FinalizeBlock drops it.
**Exploit:** Spam 64 self-transfers (0.64 ZCRYPT in gas) in one block to invalidate every honest tx in flight; repeat each block. No soundness impact, but denial of service on the whole shielded pool.
**Fix:** Window by block (record one root per block, retain e.g. 100+ blocks, as Zcash does) or raise the append window by orders of magnitude.

### 3. LOW: `postcard::from_bytes` ignores trailing bytes, so `tx.proof` and therefore `txbind` are malleable
**Location:** `tall.rs:565` (and `lib.rs:983`); `postcard/src/de/mod.rs:12-19` (`from_bytes` never calls `finalize`; `take_from_bytes` does). `shield_tx.rs:97` hashes raw proof bytes into `txbind`; the outer codec's trailing-byte check (`shield_tx.rs:392`) does not cover bytes inside the length-prefixed `proof` field.
**Exploit:** A relayer appends junk to `proof`, the tx still verifies, but its `txbind`/CometBFT hash differ. Wallets tracking by txbind miss confirmation; two variants can coexist in mempools (second fails as double-spend). No theft.
**Fix:** Use `postcard::take_from_bytes` and reject a non-empty remainder.

### 4. LOW: global panic-hook swap in `verify_tall` is process-wide, non-reentrant state
**Location:** `tall.rs:589-595` (`lib.rs:1009-1016` same).
**What:** `take_hook`/`set_hook` mutate the process hook. The ABCI node serializes verification behind `Arc<Mutex<State>>` (`main.rs:853`), so the race is not reachable there today, but any concurrent caller (wallet, tools, future parallel CheckTx) can leave the process hook permanently silenced or lose panics from unrelated threads during the window.
**Fix:** Remove the hook swap; `catch_unwind` alone contains the panic. Better, make deserialization/shape validation return errors and treat any verifier panic as a hard bug to log.

### 5. INFO: preprocessed verifier key is recomputed on every verify and never pinned
**Location:** `tall.rs:561-564`.
**What:** Correctness relies on `setup_preprocessed(verifier_config())` being byte-identical across every node binary (seed-0 salts in the hiding MMCS, `hiding_mmcs.rs:126-130`). A Plonky3 or `rand` bump that changes salt derivation would split consensus silently (all proofs fail on upgraded nodes only).
**Fix:** Compute the vk once (lazy static) and assert its commitment against a hard-coded constant with a test; also saves a Keccak Merkle commit per verification.

### 6. INFO (privacy): anchor root reveals the exact tree length at proving time
**Location:** public input `root` (`tall.rs:511-513`), window semantics (`node.rs:253-262`).
**What:** Because a root exists per append, the anchor identifies the exact leaf count when the wallet fetched its path, a finer timing fingerprint than a per-block anchor. Combined with wallet fetch behavior this weakly links a spend to a recent receive. Fixing finding 2 (per-block roots) also fixes this.

### 7. INFO: no leaf/node domain separation in the Poseidon2 tree
**Location:** `lib.rs:611-619` (leaf preimage) vs `lib.rs:680-684` (node preimage), both 16 lanes.
**What:** Opening an internal node as a coin would require lane 15 = 0 and pk = (l6, l7, r0..r5) to be a known `Poseidon2(ss)` (2^248 preimage), so it is not exploitable; noting only that safety rests on the pk structure rather than an explicit tag.

## Score

**Circuit soundness: 8.5/10** for the AIR itself, **4/10 for the shield statement as deployed.** The constraint system is tight: every lane of every core block is bound, range checks cover all value lanes including the dummy, the carry argument is a genuine integer identity with comfortable field headroom, membership is a full 32-level in-circuit path with verifier-committed selectors and correct row gating, nullifiers are canonical and bound to the ownership secret, and Plonky3's verifier checks vk degree, public-value count, and observes everything relevant. I found no way to violate conservation, forge membership, or double-spend with the circuit's own rules. The deployed statement, however, quantifies asset identity over a 31-bit lane while the registry issues 64-bit ids without reduction, and registration is permissionless; that single u64→field mapping lets an attacker mint counterfeit zBTC or native ZCRYPT with ~2^31 work. It is a boundary bug, not a constraint bug, but it is complete, cheap, and fatal to supply integrity, so it dominates the deployed score.

**Circuit-level privacy: 8/10.** Public inputs are outputs, fee, nullifiers, root, chain tag, and a note digest: no amounts, asset, arity, or leaf position. The dummy nullifier is keyed on a secret per-coin tag so short spends are indistinguishable; hiding uses `HidingFriPcs` (ZK mode, 4 random codewords, quotient randomization) with fresh OS-seeded ChaCha20 per proof and three independent MMCS RNGs. Deductions: the per-append anchor exposes exact tree length at proving time (finding 6); the fee is public by design (main transfers use fee 0 plus a separate ZCRYPT gas tx, so this reveals little, but burn-locks pay in-asset and expose that value); and Plonky3's ZK mode is documented as best-effort rather than formally proven, so the "hiding" claim inherits that caveat.

## 3. Findings

**H1 (High): the reusable Normal-address spend pk is published in plaintext by every non-transfer action, and the wallet always uses it.**
Location: `wallet/src-tauri/src/main.rs:2634` (claim_rewards → `w.account.pubkey()`), `:2721` (claim_fees), `:3182` (mint_asset claimer pk), `:2272, 2520` (`reward_address()` = H(same pk)); `impl/bridge/src/swap.rs:711` (0x64 claimer pk = `alice.pubkey()`), `:1496-1511` and `:1196` (0x5D/0x67 refund pk = `alice.pubkey()` / `user.pubkey()`, change output to `alice.pubkey()` with note to `normal_address()`); wire formats at `abci main.rs:340-355, 381-405, 408-420, 493-511`.
What: the `zc1…` address is literally `kind ‖ pk(64) ‖ ek` (`keys.rs:138-150`). Anyone who has ever been given the address can grep the chain for those 64 bytes and recover the owner's complete staking income (0x58 amounts), bridge-fee income, every BTC→zBTC shield (0x64: amount, Bitcoin txid, BTC refund key), every zBTC→BTC redeem (0x67: amount, BTC payout key), every in-pool swap (0x62 counterparties + amounts), plus the reward address that ties every BOND/DELEGATE to it (`keys.rs:479-481` is a plain hash of pk, invertible by dictionary once one claim is seen). The resulting coins are minted with deterministic public blinds (`keys.rs:484-500, 555-571`), so the observer also knows exactly which tree leaves that identity owns and their values (first spend remains unlinkable, since the nullifier needs `spend_secret`, `lib.rs:628-637`).
Scenario: merchant M receives Alice's address for a payment; M later sees Alice's pk in 0x64/0x67 txs → M learns Alice's Bitcoin deposit/payout keys, the raw BTC txs, amounts, and her validator/delegation income. Combined with the explorer, which renders these pks (`decode.rs:142-147, 185-188, 239`), this is a public lookup.
Fix: derive a fresh stealth sub-account per action (the wallet already scans `stealth(0..next_change+20)`): claimer pk, refund pk, counterparty pk, and `reward_address(stealth(i).pubkey())` per bond/delegate; make `reward_address` a commitment with a salt rather than `H(pk)`; move claims to a shielded-claim proof (prove ownership of reward address without publishing pk).

**H2 (High): nullifier "is it spent?" queries to the node are deanonymizable by intersection and by later insertion.**
Location: `wallet/src-tauri/src/chain.rs:353-415` (one `/prove/<key>` GET per key, sequential; decoys = fresh random 32-byte keys each call, lines 401-404), called for every unspent coin on every refresh (`main.rs:2054-2083`) and before a bearer sweep (`main.rs:790`); server side `abci main.rs:2389-2412`.
What: random decoys are never in the registry and are regenerated per call; the real keys are stable across refreshes and eventually get inserted at spend (`node.rs:1545`). The RPC operator (a) intersects two refreshes on the same IP/Tor circuit → exact set of the wallet's unspent nullifier keys and their count (batch = max(32, n) leaks n when >32); (b) when a queried key is later inserted by a 0x55, attributes that transfer to the querying session and to all its other keys; (c) the reshape flow performs a self-send, a refresh (queries), then the real send within seconds on one connection (`main.rs:1712-1716, 1731-1732`), handing the operator the full link. The Rewards tab additionally sends the Normal pk itself to the node (`/staking/claimable/<pk>`, `/staking/claim_index/<pk>`, `/staking/fees/<pk>/<asset>`, `main.rs:2637-2640, 2699-2721`), so the operator gets {session → pk → coin set → spends} (whether the UI polls these automatically: UNCONFIRMED, Rewards.tsx not fully read).
Fix: never query. The wallet already downloads every tx-bearing block; extract `inputs[].nullifier` from every embedded shield tx, apply `nf_registry_key`, and mark spends locally (zero network). If a remote check must remain: fetch the whole SMT leaf list (`node.rs:320`), or use deterministic decoys drawn from already-published nullifiers plus a persistent decoy set, and batch into one request.

**H3 (High): bridge linkage is total by design and made worse by static keys and Bitcoin address reuse.**
Location: 0x64 embeds `raw_tx` + `merkle_block` + `reserve_pk` + `refund_pk` (`abci main.rs:340-355`; `swap.rs:704-712, 811-819`); 1:1 amount enforced (`main.rs:3247-3252`); refund key static per seed `h("BTCALIC", seed)` (`main.rs:2829-2834`) and used in every HTLC script (`swap.rs:695, 807`; `bridge/lib.rs:87`) which is revealed in the Bitcoin witness on sweep (`swap.rs:1095`); reserve pk pinned per asset (`swap.rs:220-224`); self-custody deposits always spend to `receive_address(0)` and change to `change_address(0)` (`selfcustody.rs:66-67, 108`); redeem publishes `btc_claim_pk` (`swap.rs:1196`) and the user reveals the ZCrypt hashlock's preimage on Bitcoin (`swap.rs:1272-1280`).
Scenario: every Bitcoin HTLC contains the same reserve key (clusters all bridge deposits on Bitcoin) and, per user, the same refund key (clusters all of one user's deposits), and the 0x64 tx pairs that key with the claimer shield pk (H1). A chain-analysis firm links: BTC UTXO history → HTLC → 0x64 → shield pk → staking/redeem history → BTC payout key.
Fix: per-deposit refund key (`h(seed ‖ counter)`), per-deposit claimer stealth pk, rotate reserve keys per epoch (the registry already supports authority rotation), fresh BIP-84 indices for receive/change. Amount and timing correlation are inherent to an SPV-proven 1:1 peg; document them.

**M1 (Medium): the "private in-pool swap" (0x62) is transparent in parties, amount and asset.**
Location: `node.rs:779-826`, `abci main.rs:408-420`, `decode.rs:176-193, 368-376`. Both 64-byte shield pks, value, asset id and hashlock are plaintext; settlement mints a deterministic-blind coin (`node.rs:919`, `keys.rs:569-571`). Only the funding coins are hidden. Known Phase-3 TODO; until then it should not be described as private.
Fix: committed values (Pedersen/Poseidon commitment + range proof in the lock), stealth party pks, hashlock blinded per leg.

**M2 (Medium): staking is transparent and persistently linked to the shield identity.**
Location: `abci main.rs:561-640`, `wallet main.rs:2389-2391` (delegator ed25519 key deterministic from the seed), `keys.rs:479-481`, `/staking/validators_json` (`abci main.rs:2157-2228`) exposes reward_address, earned, unclaimed and every delegation. The pledge shield tx's change output is known to be validator-owned (its note is decryptable only by the stealth change account, so the leak stops there).
Fix: see H1; additionally salt reward addresses and let the delegator key be per-delegation.

**M3 (Medium): wallet-to-node metadata and plaintext RPC.**
Location: broadcast to a single RPC node with `broadcast_tx_commit` (`chain.rs:419-441`); incremental leaf sync reveals the wallet's cache frontier (`chain.rs:276-320`); `nonempty_heights(scan_height+1..)` reveals last-sync height (`chain.rs:448-472`, `main.rs:2030`); CometBFT RPC is plain HTTP on 0.0.0.0:26657 with CORS * (`chain/docker/cometbft-entrypoint.sh:26-28`), and the wallet's node URL is `http://` (`Settings.tsx:134`). With Tor to a clearnet node, the exit relay sees the plaintext RPC (queries + txs). Mempool `/unconfirmed_txs` is CometBFT default (not overridden), so any peer sees first-seen times.
Fix: publish `.onion` node endpoints (end-to-end encrypted, no exit), or TLS; add Tor stream isolation per request class; random delay/jitter before broadcast; consider submitting via a random peer instead of one configured node.

**M4 (Medium): Esplora is address-oriented and third-party by default.**
Location: default `https://blockstream.info/api` (`wallet main.rs:903-905`); gap-limit scan sends every derived address (`esplora.rs:205-216`), plus `/tx/{txid}/status`, `/tx/{txid}/outspend`, HTLC address queries. Even over Tor the operator links the user's whole BTC address set + HTLC txids within a session. The local bitcoind RPC is not proxied (`bridge/lib.rs:33-34`), acceptable for loopback.
Fix: own Esplora/Electrum over an onion service, or BIP-157 client-side filtering; at minimum per-address circuit isolation.

**L1 (Low): bridge-crate builders fingerprint themselves via note length.**
`swap.rs:603` (`vec![vec![], chg_note]` in `build_transfer` → a 0x55 whose gas slot 0 is an empty note) and `swap.rs:1508` / `:1194` (`vec![vec![1; 8], change_note]` in burn-locks). The Tauri wallet path uses proper cover notes, so this distinguishes bridge-bin/foundation/LP transfers from user transfers. Fix: use `keys::cover_note_bytes()` everywhere.

**L2 (Low): anchor root reveals wallet staleness.** ROOT_WINDOW = 256 (`node.rs:137`); the wallet fetches leaves at send start (`main.rs:1749`) then proves (seconds). A root older than the tip leaks roughly the proving latency of that client. Same class as Zcash anchors. Fix: re-fetch leaves and rebuild the path immediately before broadcast, or always anchor on the latest root at broadcast time.

**L3 (Low): node logging.** Every check_tx/finalize logs type, size and timestamp to stderr, and rejection reasons include 8 bytes of the offending nullifier key (`abci main.rs:1312-1321, 1823`, `node.rs:1541, 1607`). No IPs in ABCI logs; CometBFT's own RPC access logging not audited (UNCONFIRMED).

**L4 (Low): share links leak payment secrets off-Tor.** `wallet/src/lib/api.ts:83-91` puts the bearer coin / stealth note into `wa.me`, `t.me`, `mailto:` URLs opened by the OS browser (`main.rs:1900-1906`). A stealth note reveals (value, blind), identifying the on-chain commitment; a bearer coin is the money itself.

**L5 (Low): view key is unscoped and only partially useful.** The view key is the raw ML-KEM dk (`kem.rs:58-60`, `keys.rs:303-308`): permanent, irrevocable, not limitable by time or tx; it cannot see spends (nullifiers need `spend_secret`) or change (stealth sub-accounts), so an auditor sees receipts but not balances. No outgoing viewing key exists. Fix: derive dk per epoch (HD ML-KEM), add an OVK-style sender record.

**Info I1:** `socks5h://` is not a scheme ureq 2.12.1 recognises (`proxy.rs:124-125`); the wallet keeps such a string verbatim (`main.rs:945`), `Proxy::new` fails, and the request fails closed (`chain.rs:39-43`). Correct behaviour, but silent; document that `socks5://` already resolves inside Tor.
**Info I2 (PQ):** note encryption is genuinely PQ (ML-KEM-768, `kem.rs:1-2, 8`); commitments/nullifiers Poseidon2; proof hash-based. Classical primitives (ed25519 in BOND/UNBOND/DELEGATE `abci main.rs:561-640`; secp256k1 ECDSA open_auth `spv.rs:145-180`; Bitcoin HTLCs) only link identities that are already plaintext (H1/H3). A quantum break yields no shield secrets: BTC keys are `h("BTCBRDG"/"BTCALIC", seed)` (`main.rs:2831-2832`), delegator key `h("ZC-DELEGATOR-KEY", seed)`, BIP-84 uses hardened account paths (`hdwallet.rs:60`), and the ZCrypt seed is `h("ZC-SEED", bip39_seed)` (`keys.rs:213`). Forgery of staking signatures is a theft risk, not a privacy one.
**Info I3:** fee uniformity holds for 0x55; pledge/lock txs carry an in-tx fee `≥ MIN_FEE` (`node.rs:733, 804`, `abci main.rs:1035, 1065`); the wallet always pays exactly MIN_FEE (`main.rs:2368`, `swap.rs:1507`), so any client paying more fingerprints itself.

## 4. Comparison

Against Zcash Orchard, ZCrypt matches the whole-pool anonymity set, fixed 2-in/2-out shape and flat fee, and adds post-quantum note encryption and proofs, but it lacks diversified addresses and outgoing viewing keys: Orchard's one seed yields unlimited unlinkable receiving addresses with no extra backup, whereas ZCrypt's single reusable Normal pk is exposed by every claim, mint, redeem and swap, and its random stealth addresses must be backed up separately. Against Monero, the shielded transfer is stronger (whole tree vs ring-16, hidden asset), but Monero makes every output a one-time key by default and its wallets learn spent status by downloading the key-image set rather than asking a node per key image; ZCrypt's `/prove/` decoy batches are closer to a light-wallet "send me my key images" pattern that both ecosystems treat as a deanonymization vector. On the network side ZCrypt is ahead on defaults (Tor on, fail-closed, no DNS leak) but behind on propagation (single RPC node, plaintext HTTP, no Dandelion++-style diffusion) and, like every HTLC/SPV bridge, offers no cross-chain privacy at all.

## 5. Score

- **Protocol layer: 6.5 / 10.** The 0x55 transfer itself is excellent (whole-tree membership, hidden amount and asset, padded arity, flat fee, PQ encryption bound into the proof). The score is pulled down because every other value action (claim, bond, delegate, mint, bridge, swap) is fully transparent and is keyed by the same reusable spend pk that appears inside the payment address, and settlement coins carry public openings; the "private swap" is not private yet.
- **Wallet + network practice: 5.5 / 10.** Strong defaults (Tor on and fail-closed, hostname resolution inside Tor, full leaf download, local trial decryption, stealth change accounts, cover notes). Undermined by the per-nullifier spent-check queries (H2), transmitting the Normal pk to the node for reward lookups, reuse of the Normal pk and static BTC keys in bridge/staking flows (H1/H3), plaintext RPC to a single node, third-party address-indexed Esplora, and Bitcoin-side address reuse.

## Findings

### C1. Critical: sentinel voting power is silently overwritten (and duplicated) by the ordinary validator-set diff
**Location:** `main.rs:772-797 validator_updates()`, `main.rs:1865-1874`, `node.rs:1364-1420 sentinel_update()`, `chain/LAUNCH.md` step 4.3 ("Bond the genesis validator"), `chain/docker/cometbft-entrypoint.sh` (`FOUNDATION_SENTINEL` defaults true).
**What:** `validator_updates(before, after)` diffs `staking.validator_set()` by consensus pubkey and emits `(pk, voting_power(stake+delegated))` for every changed entry. It does not exclude the sentinel key. `sentinel_update()` only emits when `2*others+1` changes, and tracks `Sentinel.power` independently. The launch runbook bonds the sentinel key itself.
- Clobber: any block in which the sentinel's own `stake+delegated` changes but `others` does not emits only `(S, voting_power(S.stake))`. CometBFT drops S from e.g. 40,001 to ~10,000 while the app still believes it holds >2/3. Anyone can trigger this permissionlessly with a dust DELEGATE (>= 1 ZCRYPT so the whole-ZCRYPT power changes) to the sentinel key.
- Duplicate: any block where the sentinel's own stake changes AND `others` changes (or a retire fires) pushes two `ValidatorUpdate`s for the same pubkey. CometBFT 0.38 `processChanges` returns "duplicate entry", `ApplyBlock` fails, every node stops at that height and replay fails identically on restart.
- Also: the sentinel unbonding as sole validator emits `(S, 0)` -> "empty validator set" error -> permanent halt.
**Attack:** (a) With S bonded at 10k and the attacker holding one 10k validator: delegate 1 ZCRYPT to S in a quiet block -> S deflated to 10,001 vs attacker 10,000 -> attacker >1/3, can halt the chain by withholding votes, indefinitely (S never re-inflates because `others` never changes and the attacker censors nothing but simply stops voting). With >20k the attacker exceeds 2/3 and captures the chain (censorship, equivocation/fork of the bridge). Intended threshold was 1M ZCRYPT across 4 validators with a 1000-block dwell. (b) One block containing "delegate 1 ZCRYPT to S" + "delegate 1 ZCRYPT to V" -> duplicate update -> permanent halt for ~2 ZCRYPT.
No unit test or e2e covers a bonded sentinel (`testnet-init.sh` never sets `foundation_sentinel`; `sentinel_is_removable_and_auto_decays` calls `node.bond` directly, bypassing `validator_updates`).
**Fix:** Exclude the sentinel key from `validator_updates` (filter both snapshots) and make `sentinel_update` the sole emitter for S; have it emit whenever either `desired` or the sentinel's own bonded stake changed; persist the last emitted power; add an ABCI-level test "sentinel bonds / gets delegation / unbonds". Consider forbidding UNBOND of the sentinel while it is the sentinel.

### C2. Critical (economic): CLAIM (0x58) and CLAIM_FEE (0x66) are unauthenticated, gasless, and attacker-chosen in amount: anyone can shred a victim's claimable balance into unspendable dust
**Location:** `main.rs:493-511 parse_claim/parse_claim_fee`, `main.rs:1101-1123` (CheckTx: only `amount>0 && amount<=claimable`), `main.rs:1497-1547` (DeliverTx), `node.rs:1519-1550 claim_rewards`, `keys.rs:537-551 claim_chunks`.
**What:** The payload is `pk || amount` with no signature and no fee. Coins are minted to `pk` (so not stealable) but the attacker controls granularity. `rewards` also holds returned unbonded stake (`staking.rs:334-355`), and the foundation's vested tranche is claimable through the same path. A validator's `pk` is public after its first CLAIM (payload carries pk in clear) and to anyone it has received a normal-address payment from.
**Attack:** Bot watches for a victim's unbonding release (10k ZCRYPT) or per-epoch rewards and submits `amount = 1` (or 5,000 atomic, below the 10,000 MIN_FEE) claims. 2M claims of 5,000 units = ~146 MB of block space (~7 blocks at 21 MB) shreds 10,000 ZCRYPT into coins each worth less than the gas required to consolidate two of them. Value is destroyed for zero cost. Side effect: each claim appends a tree leaf and rolls the anchor window (see H2).
**Fix:** Require a signature from the shield spend key (or an ed25519 claim key bound at bond time) over `chain_id || pk || amount || nonce`; and/or only allow full-balance claims; and/or enforce a minimum chunk (>= 1 ZCRYPT) except the final remainder.

### H1. High: gasless state-creating transactions allow free, permanent state bloat (chain slowdown to halt)
**Location:** `main.rs:1125-1157` (REGISTER, HTLC_OPEN CheckTx), `main.rs:1548-1596` (DeliverTx), `asset_registry.rs:93-152`, `htlc_shield.rs:209-233` (escrows never removed), `htlc_shield.rs:323-368 root()` O(n) per block, `state_db.rs:327-337` (whole blob rewritten every commit), `main.rs:1911 write_backup_file` (entire state serialized every block).
**What:** REGISTER and HTLC_OPEN burn no gas. An attacker registers an asset with its own 1-of-1 ML-DSA keyset (u64::MAX cap) and floods HTLC_OPEN (~5.4 KB each, value=1): ~4,000 permanent escrows (~1.2 MB of consensus state) per 21 MB block. Every subsequent block re-hashes and re-serializes all of it (RocksDB blob + postcard backup) under the state lock. Tickers are likewise free to squat (26*36^9 namespace, first-mint-wins, includes squatting `zBTC` itself before `bridge_init`: see M4).
**Fix:** Charge MIN_FEE (a bundled ZCRYPT gas note like 0x55) on every state-creating tag; add expiry/pruning for settled escrows; cap escrow timeout horizon.

### H2. High: anchor-root window is 256 appends, not blocks: cheap total censorship of shield transfers
**Location:** `node.rs:140 ROOT_WINDOW = 256`, `node.rs:241-252 append_and_record`, `node.rs:1596-1600` / `node.rs:1680-1683` (anchor check at CheckTx and DeliverTx).
**What:** A root is recorded per leaf append and only the last 256 survive. One transfer appends 4 leaves (2 gas + 2 main), a CLAIM appends 1. 64 transfers or 256 one-unit self-claims (C2, free) per block invalidate every proof built against an earlier root. STARK proving takes longer than a block, so all other users' transfers fail with "unknown/expired anchor" for as long as the attacker keeps going (~0.000256 ZCRYPT/block of the attacker's own rewards, recycled).
**Fix:** Keep one root per block boundary for N blocks (e.g. 1,000 to 10,000), independent of append volume; optionally also keep the most recent K intra-block roots.

### H3. High: per-block work is O(total state); nullifier SMT root recomputed from scratch every block and on every `/app/hash` query
**Location:** `smt.rs:121-148 subtree()/root()` (no node cache; ~n*(256-log n) SHA3 + range probes per call), called from `node.rs:369 state_root()` in `main.rs:1888` (every block), `main.rs:933` (`info`), `main.rs:1982` (`/app/hash`), `main.rs:1948` (`/registry/root`), `main.rs:2389-2411` (`/prove`); `state_db.rs:317-323` re-puts every nullifier every commit; `node.rs:1660-1662 commitment_leaves()` and `/commit/leaves` clone the whole tree per query.
**What:** At 1e5 nullifiers a single root is ~2.4e7 hashes (seconds); at 1e6 it is minutes. 1 s block target. Every transfer adds 4 nullifiers for 0.01 ZCRYPT. Public RPC (`rpc.*` via Caddy, CORS `*`) can call `/app/hash` in a loop; each call holds the state mutex through a full root computation, starving `finalize_block`. Nullifiers are never pruned so degradation is permanent.
**Fix:** Cache SMT internal nodes and update incrementally on insert (as `CommitmentTree` already does); cache `state_root()` per height and serve queries from the cache; write only new nullifiers in `commit`; paginate `/commit/leaves`; make the postcard backup periodic, not per block.

### H4. High: SPV mint `open_auth` binds only `(outpoint, claim_pk)`: a mempool front-runner can open the depositor's escrow with `value = 1` or an already-passed timeout
**Location:** `spv.rs:169-182 verify_open_auth` / `open_auth_digest`, `node.rs:504-530 htlc_open_spv` (value/timeout are unbound tx fields; `claim_outpoint` burns the deposit), `spv.rs:612-617` (`out.value < value` allows any smaller value), CheckTx `main.rs:1181-1191` does not even call `verify_open_auth`.
**Attack:** Copy the victim's 0x64 tx from the mempool, keep proof + open_auth + claim_pk, set `value=1` (or `timeout_height=0`). The escrow opens for 1 sat and the BTC outpoint is marked claimed forever. If the victim's wallet auto-claims the escrow for its `claim_pk`, the preimage is revealed and the reserve key sweeps the full BTC deposit against 1 sat of zBTC (theft; UNCONFIRMED whether the wallet auto-claims). Otherwise the deposit is griefed until `btc_locktime` refund. Free, repeatable, kills the bridge.
**Fix:** Include `asset_id || value || timeout_height || hashlock` (and chain_id) in `open_auth_digest`; verify `open_auth` in CheckTx.

### M1. Medium: BTC_HEADERS replay of already-known headers is free and costs a full header-chain clone per tx
**Location:** `spv.rs:400-427 precheck_headers` (returns Ok when the first header is already known), `spv.rs:437 submit_headers` (`self.clone()` unconditionally), `main.rs:1176-1180,1696-1710`.
**What:** Replaying overlapping windows of known headers (up to 2016*80 = 161 KB, unlimited distinct variants) passes CheckTx and DeliverTx (`accepted=0`, code OK) with no fee. ~130 such txs fit a block, each cloning the entire index/log (grows ~52k headers/year) under the consensus lock.
**Fix:** Reject batches where every header is known (or where the last header is known); skip the clone when nothing new; charge gas.

### M2. Medium: fee-less tags that pass CheckTx but always fail (or do nothing) at DeliverTx fill blocks for free
**Location:** UNBOND CheckTx `main.rs:1050-1055` (no `is_validator` check: any fresh key with nonce 0 passes), BTC_REANCHOR CheckTx `main.rs:1192-1200` (structural parse only, payload up to `max_tx_bytes = 12 MB`), HTLC_OPEN with attacker-owned asset (H1).
**What:** Free 21 MB/s of junk propagated and stored by every node; validators' bandwidth/disk DoS.
**Fix:** Mirror DeliverTx preconditions in CheckTx (validator exists; an immature mint with that outpoint exists) and charge gas on every tag.

### M3. Medium: CheckTx runs full STARK verification under the global state mutex, uncharged
**Location:** `main.rs:1002-1005` (`self.locked()` for the whole CheckTx), `node.rs:1670-1690`, `shield/lib.rs:939-974`; `max_tx_bytes = 12000000` in all entrypoints.
**What:** A valid proof with one flipped byte deserializes fine and fails only at the end of verification (tens to hundreds of ms). Rejected txs pay nothing. Public RPC lets anyone serialize hundreds of ms of CPU per request against the same mutex `finalize_block` needs; CometBFT recheck re-verifies every pending proof each block.
**Fix:** Verify proofs outside the state lock (clone the tiny root window + nullifier membership snapshot), rate-limit/size-limit at the RPC edge, cache verified tx hashes across recheck.

### M4. Medium: `zBTC` registration is a permissionless first-come race that permanently binds the bridge reserve key
**Location:** `main.rs:1125-1140,1548-1566`, `asset_registry.rs:93-152`, `chain/LAUNCH.md` "Registering zBTC on mainnet" ("whoever runs bridge_init first PERMANENTLY binds zBTC").
**What:** Any party can send REGISTER `zBTC` with a 33-byte reserve pubkey (SPV form) for free. Whoever lands first owns the reserve key that every deposit HTLC must be claimable by; the operator learns preimages from on-chain claims and holds all bridged BTC with no obligation to honor redeems. Mitigated only by the foundation proposing every block early on and registering promptly.
**Fix:** Register zBTC (reserve key) in genesis `app_state` at InitChain, or restrict `zBTC` registration to the foundation address / a governance key.

### M5. Medium: sentinel auto-decay "4 distinct validators" is Sybil-trivial
**Location:** `node.rs:1380-1395`, `SENTINEL_DECAY_MIN_VALIDATORS = 4`, `SENTINEL_DECAY_DWELL_BLOCKS = 1000`.
**What:** `n_others` counts entries in `validators`; one actor with 4 x 10k self-bonds and 1M delegated satisfies it and, after 1000 blocks (~17 min), retires the guarantor while holding 100% of external power. Combined with C1 the threshold is effectively ~20k, but even fixed, the distinctness check adds no security.
**Fix:** Drop the illusion or use a Nakamoto-coefficient style check (no single validator > 1/3 of external power) plus a longer dwell.

### L1. Low: Sentinel (`retire`, `decay_streak`, `power`) is persisted but excluded from `app_hash`
**Location:** `node.rs:73-80` (comment "NOT part of the app_hash"), `state_db.rs:254-260` (missing `blob/sentinel` silently loads as `None`).
**What:** A node restored without the sentinel blob computes identical app_hashes but different validator updates; divergence surfaces only at the next `NextValidatorsHash` mismatch. Fold it in for early, deterministic detection.

### L2. Low: RocksDB path has no snapshot/blob format version; `#[serde(default)]` has no effect under positional postcard
**Location:** `state_db.rs:22 STATE_DB_SCHEMA = 1` (key layout only), `state_db.rs:262-275` synthesizes `version: SNAPSHOT_VERSION_PUB` without reading one; `staking.rs:57-73`, `node.rs:100-130` `#[serde(default)]`.
**What:** A blob written by an older binary decodes positionally into the new layout (error or garbage). In practice CometBFT's handshake app_hash comparison catches garbage, so it fails closed, but the "refuses to load rather than misparse" guarantee does not hold on the DB path. Persist `SNAPSHOT_VERSION` in `meta/` and check it in `load()`.

### L3. Low: chain_id fallback and stale runbook pointers
**Location:** `main.rs:31 DEFAULT_CHAIN_ID`, `main.rs:172-177 load_chain_id` (sidecar file, falls back to `zcrypt-1`), `chain/LAUNCH.md` step 2 (cites `main.rs:30 CHAIN_ID`, no such constant).
**What:** Losing the `.chain_id` sidecar on a non-mainnet chain makes that node reject every valid tx (node-local halt). Store chain_id inside the RocksDB meta.

### L4. Low: `mint_message` / `rotate_message` omit chain_id
**Location:** `mint_auth.rs:95-119`.
**What:** Asset ids are chain-independent by design, so a treasury signature for testnet replays on mainnet if the same keyset is registered on both. Add chain_id to both messages.

### I1. Info
- Evidence params: CometBFT default `evidence.max_age_num_blocks = 100000` (~28 h at 1 s blocks) is far shorter than the 10-day unbonding period; raise it in the genesis consensus params (`chain/docker/*.sh` set none).
- Emission and vesting are per height; actual block interval is `timeout_commit` plus consensus latency, so real-time issuance runs ~20-30% slower than nominal. Not a security issue, but the whitepaper numbers assume exactly 1 s.
- `CommitmentTree::append` returns `None` when full (2^32) and every caller ignores it (`node.rs:242`): at capacity outputs vanish while nullifiers are still recorded. Unreachable in practice; make it a hard error.
- `emission.rs:30-34` says claim/unbond/undelegate "debit" MIN_FEE; `staking.rs` implements them as gasless. Docs disagree with code.
- Validators pull `ghcr.io/zcryptnetwork/zcrypt-abci:latest` (`docker-compose.validator.yml:23`); a devnet-featured image would accept 0x56 SEED. Publish digests and a reproducible build.

## Centralization assessment (as the code stands)

- Sentinel: while active, one foundation key alone holds >2/3 of voting power (`node.rs:1364-1420`). It can censor any tx, halt at will, equivocate/fork (slashing removes it from staking but `sentinel_update` keeps re-emitting inflated power: it is effectively unslashable), and because BFT time and block rate follow the >2/3 set, it controls unbonding release, HTLC timeouts, and the real-time pace of emission and foundation vesting. Auto-retirement (1M external ZCRYPT, 4 validators, 1000 blocks) is Sybil-able (M5) and, with C1, bypassable at ~20k ZCRYPT by anyone, not just the foundation.
- Foundation: 20% of supply to a single reward address, claims gated only by height; the first 50k plus all early emission (foundation is the only validator at launch) concentrates stake needed to reach MIN_STAKE for months.
- Mint authority: zBTC is trustless on the mint side (consensus SPV), but the single hot secp256k1 reserve key custodies all bridged BTC and cannot be rotated; redeems depend entirely on that operator. Whoever registers `zBTC` first owns it (M4). Non-zBTC assets are minted at the discretion of self-declared M-of-N keysets with self-declared caps.
- Software supply chain: validators run an unverified `latest` image; the foundation's build flags are de facto consensus while the sentinel holds >2/3.
- Governance: no on-chain parameter changes; consensus constants (fees, MIN_STAKE, halving, window sizes) require a hard fork, which the sentinel can unilaterally impose while active.

## Scores

- Consensus/node safety: 5.5 / 10. The accounting core is genuinely sound (burn-backed stake, capped emission, exhaustive app_hash coverage, atomic fsync'd persistence, replay nonces, canonical nullifier keys, distinct-signer thresholds) and I found no inflation or direct theft path in this domain. It loses points for C1 (the liveness guarantor's supermajority can be stripped or captured for ~20k ZCRYPT, undoing the stated 1M-stake retirement design), C2 (destruction of claimable value with no cost or auth), and H4 (bridge deposit griefing with a plausible theft path).
- Liveness / DoS resistance: 3 / 10. A permanent chain halt is purchasable for about 2 ZCRYPT (C1 duplicate update); state bloat, block-space filling, header replay, anchor-window censorship and mempool proof-verification are all free or near-free; per-block work grows with total chain state (H3) so the 1 s target degrades unconditionally with use. All of these are fixable with a uniform gas requirement on every tag, CheckTx parity with DeliverTx, an incrementally maintained SMT, and a block-indexed anchor window.

## Findings

### C1. CRITICAL: CLTV timestamp/height confusion lets a depositor refund immediately and still mint
**Location:** `spv.rs:627-633` (only a lower bound on `btc_locktime`), `spv.rs:724` (`push_int(locktime)`), no `500_000_000` threshold anywhere in `impl/` or `wallet/`.
**What:** OP_CLTV treats a script number ≥ 500,000,000 as a UNIX timestamp. Consensus only checks `btc_locktime >= spv_tip + 144`, so `btc_locktime = 600_000_000` (year 1989) passes as "a height far in the future", while on Bitcoin the refund branch is spendable in the very next block (tx nLockTime = 600M, nSequence 0xFFFFFFFE, MTP ≫ 600M).
**Attack:** attacker funds HTLC(H, reserve_pk, own refund key, locktime=600M) with 1 BTC, waits 6 confs, submits 0x64 (passes), spends the HTLC via the refund branch, then claims the zBTC escrow with the preimage. The deposit tx remains in its block, so the immature mint matures normally. Unbacked zBTC, repeatable with the same BTC, bounded only by the 21M cap. The watcher's "remaining blocks" alert is also fooled (`swap.rs:1068, 1079`).
**Fix:** in `check_deposit` require `proof.btc_locktime < 500_000_000` (`LockTime::from_consensus(x).is_block_height()`), and add an upper bound (e.g. `tip + 4 * locktime_margin`) so C3 below is also constrained. Add a unit test with a timestamp-type locktime.

### C2. CRITICAL: unbounded preimage length makes the reserve sweep impossible while the mint succeeds
**Location:** `htlc_shield.rs:292`, `zvm.rs:130`, `main.rs:1748` (`&bytes[33..]` of any length, CometBFT `max_tx_bytes` = 12 MB); BTC script has no `OP_SIZE` (`spv.rs:704-732`, `lib.rs:87-110`). `MIN_PREIMAGE_LEN` (`swap.rs:379`) is client-side only and is a *minimum*.
**What:** Bitcoin consensus caps a witness element at 520 bytes; standard relay caps P2WSH stack items at 80 bytes. ZCrypt accepts any preimage that SHA-256s to the hashlock.
**Attack:** depositor picks a 600-byte preimage, deposits 1 BTC, opens the mint, claims zBTC on ZCrypt (accepted). The operator cannot build a valid claim witness (>520 B is consensus-invalid; 81..520 B is non-standard and `sendrawtransaction` rejects it). After CLTV (7 days) the depositor refunds the BTC and keeps the zBTC. Repeatable.
**Fix:** consensus: `preimage.len() == 32` in CHECK_PREIMAGE (check_tx and deliver). Script: `OP_SIZE 0x20 OP_EQUALVERIFY` before `OP_SHA256` in **both** `btc_htlc_script` (consensus) and `htlc_script` (bridge) so they stay byte-identical (this changes HTLC addresses: a coordinated cut-over).

### C3. CRITICAL: mint-escrow `timeout_height` is unbounded and never tied to the BTC locktime
**Location:** `node.rs:483-531` (no check on `timeout_height`), `main.rs:340-355`, `htlc_shield.rs:279-300` (claim allowed while `height < timeout_height`). Honest clients use tip+36h (`swap.rs:155-169`), but consensus does not enforce it.
**What:** the only thing preventing "refund BTC after CLTV, then claim zBTC" is that the ZCrypt escrow must expire well before the BTC refund unlocks. Nothing in consensus relates the two.
**Attack:** attacker opens with `btc_locktime = spv_tip + 144` (the minimum) and `timeout_height = zc_tip + 10^9`. Waits ~145 Bitcoin blocks, refunds the BTC, then claims the zBTC escrow (still open). Unbacked mint; repeatable. Even with C1 fixed this stands on its own.
**Fix:** store `btc_locktime` on the SPV escrow and gate the **claim** on the committed SPV tip: `spv.tip_height() + sweep_margin < escrow.btc_locktime` (relayers keep the tip current; the operator's watcher relays every tick). Additionally cap `timeout_height <= zc_tip + MAX_CLAIM_WINDOW` at open. Add negative tests.

### H1. HIGH: redeem watcher default finalize margin (36 h) is shorter than the BTC lock it funds (3.5 d): reserve theft
**Location:** `bridge_watcher.rs:57` (`WATCHER_FINALIZE_MARGIN` default 130 000 ZC blocks ≈ 36.1 h), `swap.rs:1384` (only `timeout >= tip + margin`), `swap.rs:1399` + `swap.rs:99-106` (locks BTC with `tip + 504` blocks ≈ 84 h on mainnet, 288 ≈ 48 h on signet, regardless of the escrow's remaining life).
**Attack:** user burn-locks N zBTC with `timeout = zc_tip + 130_000` (honest wallets use 7 d + 48 h, but the user controls it). Watcher accepts and locks N BTC for 84 h. At hour 37 the user submits 0x5C (escrow expires → zBTC refunded, `node.rs:928-950`), then claims the BTC HTLC with the preimage before hour 84. The operator's finalize fails ("escrow is not open"). Loss = N BTC per redeem, repeatable while the reserve lasts. The adversarial suite's ATTACK 5 tests the margin against itself, not against the BTC locktime.
**Fix:** derive the BTC locktime from the escrow: `btc_locktime <= btc_tip + (timeout_height - zc_tip - finalize_sla)/600` and refuse if that leaves the user < a minimum claim window; or make the default margin ≥ `btc_redeem_lock_blocks*600 + 48h` (≈ 475 200) and assert it at startup. Add a const assertion like the ones at `swap.rs:65-68` for the redeem direction.

### H2. HIGH: redeem watcher can double-fund the same escrow (crash / timeout)
**Location:** `swap.rs:1395-1410` ("claim the slot before broadcast"), but the slot lives only in memory; `watcher.rs:160-171` pushes to `state.pending` after the pass and `bridge_watcher.rs:96` saves state only after the whole tick. `Btc::fund_htlc` (`lib.rs:311-339`) broadcasts then blocks up to 3 h in `wait_confirmed`; on timeout/RPC error it returns `Err`, and `swap.rs:1408` releases the slot.
**Attack/failure:** (a) crash after broadcast and before save → restart re-funds (escrow still "open", not in `funded`/`pending`) and the first HTLC is never finalized; (b) confirmation wait > 3 h or a transient RPC error after a successful broadcast → next tick funds again. Both HTLCs share the hashlock and the user's key, so the user claims both with one preimage; the second is never burned against.
**Fix:** persist a "funding intent" (escrow id → script) before broadcast; on retry/restart check bitcoind (`scantxoutset`/`listtransactions` for the HTLC address) before funding; make `fund_htlc` return the txid on broadcast success even if confirmation waiting fails.

### H3. HIGH: zBTC ticker registration is unauthenticated and first-come: reserve-key hijack at launch
**Location:** `main.rs:1125-1140` (check_tx: only "not already registered / valid ticker / zBTC needs 33-byte key"), `main.rs:1548-1553`, `asset_registry.rs:95-160` (first-mint-wins, no fee, no signer). LAUNCH.md:131-136 and 161-167 document "whoever runs `bridge_init` first PERMANENTLY binds zBTC".
**Attack:** anyone watching the chain (or any validator) sends a 0x59 for `zBTC` with their own reserve pubkey before the foundation's `bridge_init`. The authority is one-way, so the canonical peg ticker is bound forever to the attacker's key; all subsequent deposits are sweepable by the attacker and unredeemable. Recovery requires a chain reset.
**Fix:** register zBTC in genesis `app_state` (like `foundation_addr`, `btc_checkpoint`), or gate `zBTC` registration on the foundation sentinel signature (the 0x68 machinery exists).

### M1. MEDIUM: 0x64 open is malleable beyond the recipient: front-run griefing and asset substitution
**Location:** `spv.rs:145-155` (open-auth binds only outpoint + claim_pk), `node.rs:483-531` (no bound on `value` ≤ deposit, `timeout_height`, `asset_id`); `asset_registry.rs` does not forbid two assets sharing one reserve authority (`parse_register` accepts any 33-byte key, `main.rs:451-458`).
**Attack:** a mempool observer copies a pending 0x64, keeps proof + open_auth, and rewrites `timeout_height` to the past (escrow born expired) or `value` to 1 sat, or registers `FAKE` with the same reserve key and changes `asset_id`. Consensus accepts; the victim's outpoint is burned into a useless escrow. No theft (victim refunds after 7 days), but every deposit can be stranded for free.
**Fix:** include `asset_id, value, hashlock, timeout_height` in `open_auth_digest`. Reject registering a second asset with an authority already in use.

### M2. MEDIUM: benign-reorg void is permanent and unrecoverable for the depositor, and nothing automates re-anchoring
**Location:** `node.rs:566-575` (void after `reanchor_grace` = 6 mainnet blocks, outpoint stays claimed), `swap.rs:238` (`reanchor_tx` exists) but has no caller in `watcher.rs`, `bridge_watcher.rs`, or the wallet (only `examples/reorg_sim.rs`, `reorg_defense_3node.rs`).
**Scenario:** deposit re-mined by a 1-2 block reorg, no relayer submits 0x65 within ~1 h → zBTC voided, but the preimage is already public (claim happened pre-maturity) and the deposit is back on the canonical chain → the operator's watcher sweeps the BTC (`swap.rs:1060-1100`). Depositor loses both legs; only operator goodwill returns it.
**Fix:** watcher: on `/spv/pending` entries whose block is off the best chain, build and submit `reanchor_tx` automatically. Consensus: on void, remove the outpoint from `claimed` (re-open requires the refund-key auth, so it is safe), or extend mainnet grace.

### M3. MEDIUM: free, unbounded header-relay spam with O(chain) cost per tx
**Location:** `main.rs:1180` (check_tx = shape + first-header-known only), `spv.rs:400-427` (a batch whose first header is *already known* passes regardless of the other 2015), `spv.rs:436` (full `HeaderChain` clone per delivered 0x63), no fee/gas on 0x63/0x64/0x65.
**Impact:** anyone fills every block with 161 KB txs of known headers at zero cost: permanent block-store bloat and, at ~15 MB per clone (55k headers), several seconds of CPU per 1 s block. Liveness, not funds.
**Fix:** require a gas note (like 0x55) or a per-block cap on 0x63 bytes; reject batches containing already-known headers beyond the first; avoid the full clone (validate into a scratch index, then append).

### M4. MEDIUM: Esplora fee estimates are trusted without an upper bound
**Location:** `esplora.rs:101-108` (`pick.max(1.0)`, no cap), `swap.rs:191-196` (`rate * 200`), `txbuilder.rs:40-43`, `lib.rs:543-555`.
**Impact:** a malicious/compromised Esplora (or a bug) can make the wallet pay nearly the whole HTLC or a large share of a funding tx as fees (the only guard is `fee < utxo.value`). Also unconfirmed-UTXO lies only cause failed builds; fake confirmations only cause failed opens (consensus SPV protects the mint).
**Fix:** cap fee rate (e.g. 500 sat/vB) and fee-as-fraction-of-amount; surface the fee to the user before signing.

### M5. MEDIUM: redeem liquidity griefing and no refund path for unclaimed operator HTLCs
**Location:** `swap.rs:1340-1415` (operator locks 1:1, pays the funding fee, no redeem fee), `watcher.rs:176-221` (only finalizes on claim; never refunds after CLTV).
**Impact:** a user can burn-lock zBTC, let the operator lock BTC, and never claim: the operator's BTC sits until someone refunds it manually after 504 blocks, and the fee is lost; repeatable with the same zBTC after each ZC expiry. Also dust redeems (< claim fee) fail forever and are retried every tick.
**Fix:** watcher refund path after CLTV; minimum redeem value; a small redeem fee retained on ZC expiry.

### L1. LOW: value-scaled maturity is per-deposit, so aggregate immature value at depth 6 is unbounded
**Location:** `spv.rs:104-110` (0.1 BTC per conf, floor 6), `node.rs:577`.
**Note:** splitting 100 BTC into 1000 deposits gives 100 BTC of zBTC at 6 confs; the "cost-to-reorg > value" invariant holds only per deposit. Same exposure as any 6-conf exchange, but the design comment claims more. Consider depth as a function of total immature value in a window.

### L2. LOW: deposits below the sweep fee are not economically sweepable
No consensus minimum mint value (`spv.rs:621`); a 1000-sat deposit costs ≥ 500 sat to sweep (`swap.rs:196`). If the operator skips them the depositor refunds after CLTV and keeps the zBTC. Enforce a minimum (e.g. 50k sats) in `check_deposit`.

### L3. LOW: self-custody swap aborts if 6 confs take > 3 h, leaving BTC in the HTLC with no resume in the wallet
`esplora.rs:186-200` (3 h deadline) is inside `fund_htlc` before the 0x64 is submitted; `bridge_recover` (`wallet main.rs:3440`) only reconciles zBTC coins. Funds return after 7 days via CLTV; add a resume-from-funded-UTXO path.

### L4. LOW: reserve key handling inconsistencies
Wallet reserve key = `H("BTCBRDG", seed)` (`wallet main.rs:2829-2834`); daemon takes the raw 32-byte `ZCRYPT_RESERVE_SEED` as the key (`bridge_watcher.rs:40-47`) with no derivation, and receives it via docker env (`docker-compose.yml:111`, visible in `docker inspect`/procfs). No code path prints or returns the secret (only the pubkey, `bridge_watcher.rs:60`). Document the exact export/derivation and prefer a file/HSM over env.

### I1. INFO: no future-timestamp bound (deliberate, for determinism)
`spv.rs:482` enforces only MTP. Work-based fork choice means timestamp games cannot win against honest hashpower; noted as accepted.

### I2. INFO: merkle "64-byte transaction" leaf/inner-node ambiguity (UNCONFIRMED cost)
`PartialMerkleTree` cannot distinguish a 64-byte tx from an inner node (Lerner 2017); published cost estimates are ≳2^70 and the attacker must mine such a tx on Bitcoin. Not practical today; a coinbase-depth check would close it.

### I3. INFO: no maximum reorg depth
A heavier chain reorganising back to the checkpoint is accepted; matured coins cannot be voided. Consistent with the value-scaled maturity model, but worth stating in the whitepaper.

### I4. INFO: over-collateralised deposits
`out.value >= value` (`spv.rs:621`): the excess is swept by the reserve with no zBTC minted. The wallet guards this; consensus could require equality.

## Trust assumptions a zBTC holder makes

- **Operator hot key + bitcoind wallet**: all swept BTC and the redeem float sit under one secp256k1 key and one bitcoind wallet; redeems require the operator to be online and honest (a dead operator = zBTC redeemable only via an outside market).
- **Watcher correctness/uptime**: sweeps must land before CLTV (7 d), re-anchors (currently manual) within 6 Bitcoin blocks, finalizes before ZC expiry.
- **Bitcoin security**: no >6-block (per-deposit value-scaled up to 100) reorgs; splitting makes the aggregate bound weak (L1).
- **Header liveness**: someone relays headers promptly (anyone can; the operator does); a stale SPV tip only delays maturity but after the C3 fix it also gates claims.
- **Checkpoint provenance**: the genesis-baked header/height must be independently verified (`mainnet-checkpoint.sh` pulls from one Esplora); a wrong checkpoint bricks the bridge.
- **Esplora (blockstream/mempool.space)**: cannot forge mints, but can deny service, lie about fees (M4), and learns every wallet address (Tor optional).
- **Launch race**: the zBTC ticker must be registered by the intended custodian before anyone else (H3).
- **Timing model**: 1 s ZC blocks / 600 s BTC blocks are assumed for cross-chain deadlines; the margins are compile-time constants (`swap.rs:65-68`) and hold only if operators do not lower them (H1).

## Scores

**SPV mint gate: 3/10.** The header chain and inclusion proof are well built (work-based fork choice, correct retarget, MTP, CVE-2012-2459, checkpoint discipline, deterministic, app_hash-committed) and the reserve/outpoint/recipient bindings are sound. But the *economic* gate has three independent unbacked-mint paths that need no hashpower and are repeatable with the same BTC: CLTV timestamp confusion (C1), oversized preimage (C2), and the unbounded ZC escrow timeout (C3). Each is a small, mechanical fix with tests; after them and M1/M3 the gate would sit around 8/10.

**Swap/redeem + custody: 4/10.** Scripts, sighashes, HD derivation, envelope binding and the on-chain payout key are correct, and the watcher is idempotent for sweeps. However the shipped redeem daemon defaults allow outright reserve theft via a short ZC timeout (H1), can double-fund on crash/timeout (H2), never refunds unclaimed locks (M5), and the peg ticker can be hijacked at launch (H3). Custody remains a single hot key plus a hot bitcoind wallet (documented). Fixing H1/H2/H3 and adding the refund path would bring this to roughly 7/10, with the remaining gap being single-key custody.

## Findings

### High

**H1. BTC reserve key is a plaintext environment variable on the public VPS, and a second hot copy is derivable from the operator's desktop-wallet mnemonic.**
Location: `chain/docker-compose.yml:97-123` (`ZCRYPT_RESERVE_SEED` via `.env`/environment), `impl/bridge/src/bin/bridge_watcher.rs:40-46`, `main.rs:2829-2834, 2871-2875` (`H("BTCBRDG", seed)` from the wallet that runs `bridge_init`), `chain/LAUNCH.md:131-137`.
What: the key that can sweep every bridged BTC lives in `docker inspect`/`/proc/*/environ` on an internet-facing host, and the same key is regenerable inside a networked GUI wallet process that keeps the mnemonic as a plaintext `String` (`main.rs:131`). The zBTC authority is one-way (cannot rotate), so compromise is permanent. The launch runbook also has the foundation mnemonic (4.2M ZCRYPT) restored into that same networked wallet to claim (`LAUNCH.md:26-29, 107-109`).
Scenario: any RCE/container escape on the VPS, or malware on the operator desktop, drains the reserve; no HSM, no multisig, no offline-signing path.
Fix: docker secrets or a 0600 file read once and zeroized; separate custody seed from the operator wallet; a claim-only cold flow for the foundation key (sign the 0x58 CLAIM offline, broadcast online); key-rotation path for the SPV authority before mainnet.

**H2. Validators pull an unpinned, unsigned `latest` image built from a floating nightly toolchain.**
Location: `chain/docker-compose.validator.yml:22` (`ghcr.io/zcryptnetwork/zcrypt-abci:latest`, no digest), `chain/docker/Dockerfile:3` (`rustlang/rust:nightly-bookworm`), `impl/rust-toolchain.toml` and `wallet/rust-toolchain.toml` (`channel = "nightly"`, no date), `.github/workflows/ci.yml` (no `--locked`, actions pinned by tag not SHA).
What: consensus code that every validator runs is neither digest-pinned nor signature-verified, and the binary is non-reproducible (nightly drifts daily; the only reason for nightly is the vendored `p3-util` needing `maybe_uninit_slice`, `impl/Cargo.toml:5-9`).
Scenario: a compromised GHCR account/tag, or an upstream nightly regression, ships to all validators on the next `restart: unless-stopped`/pull; nobody can reproduce a hash to detect it.
Fix: pin `nightly-YYYY-MM-DD` in both toolchain files and the Dockerfile; publish images by digest and sign them (cosign) with the digest in the compose file; add `--locked` in CI; consider dropping nightly by patching p3-util to stable-only code.

### Medium

**M1. Validator consensus private key is pasted into the wallet webview and shipped over IPC.**
Location: `main.rs:2219-2232` (`bond_validator(consensus_seed_hex, ...)`), `wallet/src/components/Rewards.tsx:227-242`, `chain/README-validator.md:29-40`.

**M2. Public RPC has no rate limit, accepts 30 MB bodies, and every CheckTx runs a full STARK verification at zero cost to the sender; validator RPC is published on all interfaces.**

Location: `impl/shield/src/lib.rs:338-348` (`chain_domain` → `field_limb`), public input at `lib.rs:928` and `tall.rs:514`.
